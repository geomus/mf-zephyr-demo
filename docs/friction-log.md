# Friction log

Every point where docs or tooling were unclear, slow, broken or surprising. Times are ART (UTC-3). Factual, with a suggestion when there is one.

The agent ran in a sandbox with no access to the home folder. Some entries come from that setup, and those say so.

## 2026-11-20 · Reading the docs

- **I did not find a definition of "Default Cloud integration" in the docs I read.** The architecture page describes a "Managed Infrastructure Model" for "the default configuration", and the Cloudflare page says "default (managed)". The Cloudflare page also lets any custom integration be "Set as Default". _Suggestion:_ one sentence in the docs defining the default integration.
- **I did not find in the Quick start how you log in.** The first-app tutorial is where I read that a browser window opens on the first build. _Suggestion:_ say it in the Quick start, and say what happens when no browser is available (CI, containers).
- **Three different Module Federation imports** across the Rspack page (`@module-federation/enhanced/rspack`), the create-mf-app tutorial (`rspack.container.ModuleFederationPlugin`) and the MF guide (`ModuleFederationPluginV1`, shown without an import). The install step on the Rspack page I read does not include the enhanced package.
- **The MF guide has invalid snippets:** `remotes: ['post', follow']` is missing a quote and uses an array; a `json` block contains `name: 'post'`; the `package.json` examples in remote-dependencies contain `//` comments.
- **The Rspack page's host and remote disagree:** the host loads `mf-manifest.json`, but the remote sets `filename: 'remoteEntry.js'`, and I did not find on the page when the manifest is generated. The host's localhost URL appears as the remote URL, and I did not see a note that Zephyr replaces it on deploy.
- **I did not find an example of the `remotes` value to write** next to `zephyr:dependencies`. I found it by reading the plugin source, and the deploys confirmed it: the remote must be present in `remotes`, with a value starting with `<name>@`.
- **The docs contradict each other on `~/.zephyr`:** the first-app tutorial suggests `rm -rf ~/.zephyr`, and error ZE10018 says "Do not ... manually delete files from `~/.zephyr`".
- **The docs I read describe rollback in the dashboard only.** They mention rollbacks "through Zephyr's API", but I did not find an endpoint.

## 2026-11-21 · Building

- **16:10 · `ZE_DISABLED=true` still touches the home folder.** The plugin's type docs say "no Zephyr engine, no token, no git information, no network request". But importing `zephyr-agent` runs `ensurePrivateStoragePermissions()` at module load and creates `~/.zephyr`. In a sandbox without home access, the "disabled" build crashed with `EPERM: mkdir '~/.zephyr'`. _Workaround:_ the plugin is imported only for deploy builds (see decisions). _Suggestion:_ create storage lazily, only when Zephyr is enabled.
- **16:00 · Rspack 2 needs `@rspack/dev-server` as a separate install** for `rspack serve`. I did not see it in the install step of the Zephyr Rspack page. Not a Zephyr bug: an install step that could be added.
- **15:40 · pnpm 12 did not run inside the agent sandbox** (`ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK`, "Operation not permitted") even with writable store and cache folders. pnpm 11.28.13 works. Sandbox-specific, not Zephyr.
- **18:30 · Module Federation's default share strategy blanks the host when a remote is down.** With `version-first`, the default, the runtime fetches the remotes' entries before boot (read in `@module-federation/runtime-core` 2.9.3, `shared/index.js:321`), so `Failed to get manifest #RUNTIME-003` came before React mounted and the host's error boundary never ran. Fixed with `shareStrategy: "loaded-first"`. Module Federation behavior, not Zephyr. _Suggestion for Zephyr's MF guide:_ mention it, since a host that follows a moving tag is a case where a remote can break.
- **17:55 · First `pnpm zephyr:remote`, run by me outside the sandbox.** It asked for a browser login, and the login worked. The build ran from a working tree with uncommitted changes, on top of a commit that did not contain the app yet. I did not keep the output of that first deploy, so I cannot say whether Zephyr warned about the uncommitted changes. I also deployed the host the same way. Afterwards I deleted the whole project from the dashboard, so the next deploys start from a clean commit.
- **2026-11-21 · Deploy of the remote worked, but the app was not in the dashboard I was looking at.** The CLI printed `remote.<project>.<org>#3` and a live URL that renders the remote. The cause was on my side: the dashboard was showing my personal organization, while the app is created under the organization named after the owner of the git remote. In my run the CLI output did not show which organization the app went to. _Suggestion:_ print the organization name next to the app UID, and say in the docs how the organization is chosen.
- **2026-11-21 · Two noisy messages on a healthy remote build.** (1) `No zephyr:dependencies found in package.json` is printed for a remote that has no dependencies, so it reads like a problem. (2) A React Native error `005 Missing filename in Module Federation configuration` is printed on a web Rspack build whose config does set `filename: 'remoteEntry.js'`; the build still succeeds. The check is in `zephyr-xpack-internal` 1.8.0 (`attach_remote_bundle_name_to_metadata`, in the legacy dashboard code). It reads `bundle_name`, and I did not find any code in the installed `zephyr-xpack-internal` or `zephyr-agent` that sets that field, which would explain why it prints whatever `filename` says (searched and read, not debugged). I did not find a config option to silence it. We leave the warning. _Suggestion:_ print it only for React Native targets.
- **2026-11-21 · `remote@latest` did not resolve on my first host deploy; the examples I read use it.** The host deploy printed `Failed to resolve remote dependencies: remote@latest -> ZE40003` and still deployed, with the placeholder URL left in the host. The only tag in the dashboard for the remote is `web_latest_<username>`, which is not `latest`. The ZE40003 page I read gives debugging steps rather than likely causes. The tags page says default tags look like `web_main_yourname`; the conditions they match (CI status, branch, user, target) I only saw in the dashboard. _Suggestion:_ use a selector in the examples that works on a first deploy, or create a `latest` tag automatically.
- **2026-11-21 · The deploy could not resolve the remote but finished without an error.** It deployed a host that cannot load its remote (the placeholder URL stayed in place). `failBuild` and `ZE_FAIL_BUILD=true` do not cover it: in the installed code they only rethrow errors routed through the global error handler (configuration and upload failures), while an unresolved remote is logged as a warning (`resolve_remote_dependencies` in `zephyr-agent` 1.8.0, read, not run). _Suggestion:_ fail the build when a declared remote cannot be resolved, or at least exit non-zero.
- **2026-11-21 · Version number #3 for the first deploy after deleting the project.** The count is probably per user and survives deleting projects (two deploys before the delete, then #3 and #4). Inference, not confirmed.
- **2026-11-21 · Rollback is called "Redeploy" in the dashboard, and the docs say "Rollback".** In a tag's deployment history, each older version has a Redeploy button; that is how a tag is moved back. A tag created after the first deploy only lists versions deployed after it was created, so it has nothing to roll back to until a second deploy. I did not find in the docs I read where the button is. _Suggestion:_ use the dashboard's word in the docs, and a screenshot.
- **2026-11-21 · With two tags matching the same deploys, `latest` seemed not to follow.** After I created `latest`, the host kept showing the old remote version; after I deleted the automatic `web_latest_<username>` tag, it showed the new one. I did not isolate the cause: it could be the overlapping rules or the propagation delay below. _Suggestion:_ say in the docs what happens when two tags match the same deploy.
- **2026-11-21 · A deploy or a redeploy takes up to about a minute to show.** Expected from the docs ("within one minute to an hour"), but it matters for a live demo: wait before reloading.
- **2026-11-21 · In my run, `remote@*` was frozen into the host build.** In my run the deploy wrote one concrete version URL into the host's `zephyr-manifest.json`, so the host did not see newer versions; with a tag it did. The docs say a built host follows a tag or environment when it moves, and also list semver ranges and `*` as selectors; I did not find a note that those resolve once, at build time. _Suggestion:_ say it next to the selector list.
- **2026-11-21 · Having to create the tag by hand.** My first `remote@latest` host build failed (`ZE40003`) because no tag named `latest` existed yet, and the docs I read describe creating tags only in the dashboard, after the first remote deploy. _Suggestion:_ create a `latest` tag on the first deploy.
- **16:28 · The agent sandbox blocks local port binding** (`listen EPERM 0.0.0.0:3000`), so the agent cannot run the dev servers. Sandbox-specific.
